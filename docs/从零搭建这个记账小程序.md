# 从零搭建这个记账小程序：完整步骤与设计取舍

这份文档不是 API 手册，而是「我当时怎么想、为什么这么写、哪里踩过坑」。照着走一遍，你能独立做出类似的小程序；只看结论也能理解每一层为什么存在。

---

## 0. 先明确边界

- 只给一个人用 → 不需要注册、登录页、多用户、权限体系、分享、审核上线
- 只记收支 → 不需要复式记账、借贷平衡、多币种、账户余额联动
- 要能长期用 → 数据不能只存在手机本地（换机就没了），必须上云
- 不想运维 → 不能买服务器、不能备案域名

这四条决定了后面所有选型。**先把「不做什么」写下来，比列功能清单更重要**——调研那两个开源项目时，它们 80% 的复杂度（好友协作、多账本、企业级权限）对我来说都是负债。

---

## 1. 选技术栈：三条路，选最不耐踩坑的那条

| 方案 | 代表 | 需要什么 | 为什么没选 |
| --- | --- | --- | --- |
| 自建后端 + 小程序 | 洁账（Go + MySQL） | 服务器、已备案域名、数据库、运维 | 一个人记账，运维成本远超收益 |
| 跨端框架 + 云开发 | 小明记账簿（uni-app + uniCloud） | HBuilderX 或 npm 构建链 | 那份代码没开源后端，且是 `.nvue` + Vue2，改不动 |
| **原生小程序 + 微信云开发** | 本项目 | 只要开发者工具 | —— |

原生小程序的关键好处是**零构建**：没有 `node_modules`、没有打包步骤、没有版本冲突。你在开发者工具里改完保存就生效，出问题一定是你代码的问题，不是工具链的问题。

云开发解决的是「后端」这一层：数据库、云函数、文件存储都在腾讯云上，小程序用 `wx.cloud.callFunction` 直接调，**不需要域名、不需要备案、不需要配 HTTPS**。个人用量的费用极低（具体额度以云开发控制台为准）。

代价也要说清楚：被绑在微信生态里，换平台等于重写。对「自己用」这个场景，这个代价可以接受。

## 2. 设计数据模型：三个集合就够

```
records     一笔账
categories  分类
budgets     按月预算
```

字段设计上有三个关键决定，每个都有原因：

### 2.1 金额用「分」存整数

```js
amountFen: 2550   // 25.50 元
```

浮点数做金额会出这种事：`0.1 + 0.2 === 0.30000000000000004`。月底汇总几十笔之后，误差会显示成 `1234.5600000000001`。用整数分存，加减永远精确，只在展示时除 100。

对应代码：`miniprogram/utils/money.js` 里的 `parseAmount` / `fenToStr` / `fenToFixed`。

### 2.2 记录里冗余存分类名和图标

```js
{ categoryId: 'doc_12', categoryName: '餐饮', categoryIcon: '🍜', categoryColor: '#FF8A65' }
```

正常化设计应该只存 `categoryId`，展示时再 join。但这里故意反着来：

- 云开发没有 join，查一次账要再查一次分类，列表里 300 条就是 300 次查询（或一次 `in` 查询 + 内存拼装）
- 更重要：**用户删了「咖啡」分类之后，去年那几笔咖啡不应该变成「未分类」**

冗余快照让历史账单永远保持记账当时的模样。这条经验在大部分「单据类」系统里都成立。

### 2.3 预算按月存一条

```js
{ uid, month: '2026-11', amountFen: 300000 }
```

不做「预算模板 + 自动续期」，因为那会引入「这个月要不要沿用上月」的产品问题。每月手工设一次，逻辑最简单，也最符合个人记账的真实节奏。

### 2.4 该建索引

云开发控制台 → 数据库 → 索引管理，`records` 上建 `uid + date` 的复合索引。账单量上千条以后，有没有索引差别很明显。这一条很容易忘。

## 3. 后端写成一个入口：action 路由

`cloudfunctions/api/index.js` 只有一个 `exports.main`，用 `action` 分发：

```js
switch (action) {
  case 'record.add':  return { ok: true, data: await addRecord(uid, event) }
  case 'record.month': return { ok: true, data: await monthDetail(uid, event.month) }
  ...
}
```

为什么不做成十几个云函数？

1. 部署一次就够，改任何逻辑都不用重新上传多个函数
2. 共享代码自然（`csv.js`、`summarize()` 直接 require）
3. 冷启动只需要热一个容器

代价是单函数变胖，但对 500 行以内的业务量完全不是问题。

### 3.1 鉴权：只用 OPENID，不写登录页

```js
const uid = cloud.getWXContext().OPENID   // 微信保证这是当前用户
```

云函数里拿到的 OPENID 是微信服务端校验过、伪造不了的。所以：

- 不需要注册登录页
- 不需要自己发 token
- 不需要「用户表」——`uid` 就是用户

### 3.2 每个写操作都要校验归属

这是最容易被忽略、也最危险的一步。看这段（`record.update`）：

```js
const existed = await getDocOrNull(COL_RECORDS, input.id)
assert(existed && existed.uid === uid, '记录不存在')
```

只写 `doc(id).update()` 而不校验，就意味着**任何人拿到一个 `_id` 就能改别人的账**。虽然是自己用的小程序，`_id` 也可能从日志、调试信息里泄露。分类的改/删上也踩过这个坑，后来统一补了校验，并在测试里加了「别人的分类改不了也删不掉」这条用例。

### 3.3 返回结构统一

```js
{ ok: true, data: ... }        // 成功
{ ok: false, msg: '金额不正确' } // 业务失败
```

客户端 `utils/api.js` 只需判断 `ok`。这样「云函数报错」和「业务校验失败」在调用方是同一套处理，页面里不用写两种错误分支。

## 4. 页面骨架：先让壳跑起来

`app.json` 里定 tabBar（首页 / 明细 / 统计 / 我的），`pages/` 下一个目录一个页面，四件套：

```
pages/add/add.js    逻辑
pages/add/add.json  页面配置（标题、下拉刷新）
pages/add/add.wxml  结构
pages/add/add.wxss  样式
```

**没有图标资源也做了 tabBar**：`iconPath` 是可选的，纯文字 tabBar 完全能用。少维护一套图片，也就少了「图标没打包进去」这种坑。分类图标同理，全部用 emoji 存在数据库里。

## 5. 记一笔：整个项目最难的界面

看起来简单，实际有三个状态要管：类型（收/支）、分类选中、金额输入中。金额键盘是自绘的（不是系统键盘），因为系统数字键盘不带「完成」按钮，也没有「再记一笔」的顺滑体验。

### 5.1 金额输入必须规范化

用户可能按出 `00.`、`1.2.3`、`1.239` 这种。`money.normalizeInput` 逐条处理：

```js
'012'    → '12'
'.'      → '0.'
'1.2.3'  → '1.23'   // 第二个点被丢掉
'1.239'  → '1.23'   // 只留两位小数
```

这类「输入净化」函数一定要**纯函数 + 能单测**，因为它们最容易写错，又最容易被 UI 掩盖。

### 5.2 保存后检查是否超支

```js
const tip = this.data.type === 'expense' ? await this.overBudgetTip(month) : ''
if (tip) {
  wx.showModal({ title: '本月预算超支了', content: tip, complete: () => wx.navigateBack() })
}
```

注意 `overBudgetTip` 内部用 `try/catch` 吞掉错误并返回空字符串——提醒是锦上添花，**不能因为它失败就阻断记账**。这是「主流程」和「增强功能」的边界划分。

## 6. 明细与统计：能用 CSS 就别上 canvas

统计页有分类占比和 6 个月趋势，我**没有用 ECharts 也没有用 canvas**，而是用 `view` + 宽度百分比：

```html
<view class="ratio-fill" style="width: {{item.percent}}%; background: {{item.color}}"></view>
```

理由很实际：

- canvas 要处理设备像素比、生命周期、`canvas-id` 唯一性、层级问题
- 小程序里 ECharts 得引一份几百 KB 的定制包，还要处理 `ec-canvas` 的各种兼容
- 我要的是「一根能看懂的条」，CSS 十行就够，还自带过渡动画

**图表复杂度要和信息量匹配**。柱状图用来比较 6 个月，条形图用来表达占比，这两件事都不需要坐标系。

## 7. 账单导入：真正麻烦的是脏数据

这是整个项目里逻辑最密的一块，`cloudfunctions/api/csv.js`。

### 7.1 两个平台，两种编码

| 平台 | 编码 | 表头特征 |
| --- | --- | --- |
| 微信支付 | UTF-8（带 BOM） | `交易时间, 收/支, 金额(元)` |
| 支付宝 | **GBK** | `交易创建时间, 收/支, 金额（元）`（全角括号） |

小程序端的 JS 环境没有 GBK 解码能力，所以**解码放在云函数**（Node 自带 `TextDecoder`）：

```js
let text = new TextDecoder('utf-8').decode(buffer)
if (looksBroken(text)) text = new TextDecoder('gbk').decode(buffer)
```

判断「坏了」的方法：UTF-8 解 GBK 字节会出现大量替换字符 `\uFFFD`，占比超过阈值就换编码重解。这是个很便宜的启发式。

### 7.2 不写死列号，按表头找列

两份 CSV 列顺序完全不同，写死 `cells[5]` 一定出错。所以先**找到表头行**（同时出现「金额」和「时间」的那一行），再按列名匹配：

```js
date:      [/交易时间/, /付款时间/, /交易创建时间/, /日期/]
amount:    [/金额/]
direction: [/收\/支/, /收支/]
```

### 7.3 什么该跳过

- `收/支` 是「不计收支」→ 转账、还信用卡、余额宝转入，这些不是消费
- 状态是「交易关闭 / 已全额退款 / 交易失败」→ 钱没真花出去
- 收入行里带「退款」→ 这是原路退回，算进来会变成「支出 + 收入」双重记录

### 7.4 去重靠内容哈希

```js
hash = [date, type, amountFen, remark].join('|')
```

导入前把这个区间已有的哈希全取出来，命中就跳过。用户重复导入同一个月的账单不会变成两倍数据——这是导入功能**必须有**的行为，否则没人敢用。

## 8. 没有云环境，怎么验证代码是对的

这是很多人的死角：本地跑不了云函数，就只能靠「上传后点一点」试错。

我的做法两层：

**第一层：静态检查** `tools/verify.js`

用 `vm.Script` 编译每个 JS（只编译不执行，抓语法错误），再检查：

- 所有 JSON 能否解析
- `app.json` 里的页面，`.js/.json/.wxml` 是否齐全
- WXML 标签是否配对（自己写的栈式匹配）
- `bindtap="foo"` 的 `foo` 在对应 JS 里是否存在 ← 这个能抓掉大量「点了没反应」
- 页面调用的 `action` 是否在云函数里注册

**第二层：内存数据库跑云函数** `tools/test-cloud.js` + `tools/stub/wx-server-sdk/`

写一个 60 行的假 `wx-server-sdk`，实现 `collection/where/orderBy/skip/limit/get/add/doc/update/remove/createCollection` 和 `command.gte/lte`。然后用 `NODE_PATH` 指过去，云函数里的业务代码**原样执行**：

```bash
NODE_PATH=tools/stub node tools/test-cloud.js
```

这样能在几秒内验证：金额精度、跨月跨年、越权拦截、导入去重、CSV 两种格式。37 个用例，每次改完都跑。

**这套东西的性价比极高**：写 mock 花了一小时，后面每次改动省下的「上传—点击—发现不对—再改」的时间是几十小时。

## 9. 部署：五步，一次配好

1. **注册小程序**：mp.weixin.qq.com → 小程序 → 个人主体。拿 AppID（测试号不支持云开发）
2. **填 AppID**：`project.config.json` 里的 `appid`
3. **开通云开发**：开发者工具点「云开发」→ 开通 → 复制环境 ID
4. **填环境 ID**：`miniprogram/config.js` 的 `envId`
5. **上传云函数**：右键 `cloudfunctions/api` → 上传并部署（云端安装依赖）

第一次打开会自动建 `records`/`categories`/`budgets` 三个集合，写入 22 个默认分类。

### 自己用怎么长期打开

点「上传」→ 小程序后台「版本管理」设为**体验版** → 「成员管理」把自己加为体验成员。体验版不需要提交审核、不需要发布。

## 10. 常见坑速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 首页一直显示「还没配置」 | `config.js` 的 `envId` 为空 | 填环境 ID 后重新编译 |
| 报 `FUNCTION_NOT_FOUND` | 云函数没上传 | 右键 `api` 上传部署 |
| 报集合不存在 | 三个集合没建出来 | 控制台手动建，或再触发一次 |
| 金额显示 `12.340000000000001` | 某处用了浮点运算 | 一律用分做整数运算 |
| 导入支付宝账单全是乱码 | 客户端拿 GBK 当 UTF-8 | 解码放云函数（本项目已处理） |
| 点按钮没反应 | 事件名拼错 / 方法没定义 | 跑 `node tools/verify.js` |
| 汇总数字对不上 | 有「不计收支」被算进去了 | 检查导入的跳过规则 |

## 11. 想继续练，从这几个下手

按难度排序，每一个都能独立练手：

1. **分页加载**：明细现在一次拿整月，改成 `skip/limit` 上拉加载
2. **聚合查询**：把 `summarize()` 的 JS 汇总换成云开发 `aggregate`，顺便学 `group/match`
3. **订阅消息**：每月 1 号推送上月账单（云函数定时触发器 + 订阅消息模板）
4. **数据看板**：年视图、同比环比、消费 Top10（现在是月度）
5. **离线队列**：断网时先写本地 storage，联网后补传
6. **单元测试覆盖到页面层**：现在只测了云函数，可以用 `miniprogram-simulate` 测组件
